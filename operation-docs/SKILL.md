# 运维文档生成与管理

## 用途

当用户要求为某个中间件或服务生成/更新运维文档时，以生产环境顶级运维工程师的视角，探查服务器上该服务的实际安装位置、启停方式、配置文件、数据目录、日志位置及常见运维操作，并将总结写入 `~/agent/operation/docs/{服务名称}.md`。

## 使用场景

- 用户说：“帮我整理一下 Nacos 的运维文档”
- 用户说：“给 Redis 写个运维手册”
- 用户说：“总结下这个 docker stack 的维护方式”
- 任何涉及中间件/服务运维知识沉淀的需求

## 执行步骤

1. **确认服务名称**：
   - 从用户输入中提取服务名（如 `nacos`、`redis`、`mysql`、`mongodb`、`kafka`、`zookeeper`、`prometheus`、`grafana`、`nginx`、`docker-stack/xhd` 等）。
   - 如果名称不明确，先询问用户。

2. **探查服务现状**（仅做已授权范围内的只读探查）：
   - 进程：`ps aux | grep -i {服务名}`
   - 端口：`ss -tlnp` / `netstat -tlnp`
   - 安装目录：常见路径 `/opt/{服务名}`、`/usr/local/{服务名}`、`/etc/{服务名}`、`/var/lib/{服务名}`、`/var/log/{服务名}`
   - Docker 相关：`docker ps -a | grep -i {服务名}`、`docker images | grep -i {服务名}`、`docker stack ls`、`docker service ls`、`docker-compose ps`
   - 系统服务：`systemctl list-unit-files | grep -i {服务名}`、`service --status-all | grep -i {服务名}`
   - 启动脚本：从已定位的安装目录、systemd 单元或容器启动配置继续追踪，不默认扫描整个文件系统。
   - 配置文件：根据服务类型定位核心配置文件

3. **生成运维文档**：
   - 输出优先使用用户指定路径或该服务已有文档；否则使用 `~/agent/operation/docs/{service_name}.md`。先明确这是哪台主机的实例，不能覆盖另一环境的同名服务文档。
   - **服务名称必须使用英文小写**，例如：`nacos`、`redis`、`mongodb`、`mysql`、`kafka`、`zookeeper`、`prometheus`、`grafana`、`nginx`、`docker-stack-xhd`。
   - 以下是最低信息主题，可按服务规模组织章节：
      - **服务概述**：服务在业务链路中的用途、调用方、版本、部署方式；区分常驻进程、一次性任务和构建工具
      - **安装位置**：程序目录、配置文件目录、数据目录、日志目录
      - **启停方式**：执行主机、身份、工作目录、前置条件、命令、成功判据、失败排查和恢复方式；明确启动顺序及停止影响
      - **端口与进程**：监听端口、进程特征、健康检查方式
      - **常见运维操作**：按实际机制说明重启、配置生效、升级、日志查看、备份和恢复；备份须说明范围、保存位置、保留策略和恢复验证状态，不能把存在备份文件当作可恢复证明
      - **依赖与影响**：依赖的其他服务、重启/停止可能影响的上游/下游服务
      - **注意事项**：权限要求、数据安全、生产环境风险提示

4. **写入后验证**：
   - 沿一条代表性运维操作检查步骤是否衔接、结果是否可判断、失败是否有排查入口；路径、端口和依赖回查证据，分别记录静态确认、实际执行结果与未验证项。文档完整不等于命令已验证。
   - 向用户报告文档路径和核心结论。

5. **区分方案与实例**：
   - 可复用安装、升级和恢复方案与当前主机案例分区或分文档维护，并相互引用；实例记录主机、连接方式、资源、路径、版本及偏差，不写凭据或私钥内容。
   - 配置记录来源、用途、消费方、生效方式和缺失后果；用脱敏示例解释必要链路。不得因生成手册而修改其他工具的全局记忆。

6. **联动更新总览文档**：
   - 新增或移除服务子文档后，更新同一服务器已有总览中的索引；需要完整重建总览时使用可用的 `server-operation-index` 技能，不混入其他主机材料。
   - 若用户直接要求“生成服务器运维总览文档”或“整理 index.md”，则优先使用 `server-operation-index` 技能，而不是单独生成某个服务文档。

## 安全约束

- 探查仅使用只读操作；进程参数、配置和日志可能包含凭据，按需读取并在输出前脱敏。优先限定目录，避免默认全盘扫描。
- 编写文档不授予启停、迁移、恢复或其他写操作权限；只有用户另行授权实施时才执行。不能仅因路径不属于当前用户就自动使用 `sudo`。
- 不得在生成文档过程中擅自修改服务状态。

## 示例

用户要求：“整理 Nacos 运维文档”。

Agent 应：
1. 检查 `ps aux | grep nacos`、`ss -tlnp | grep 8848`、/opt/nacos、docker 容器等。
2. 生成 `/home/devman/agent/operation/docs/nacos.md`。
3. 报告结果。
